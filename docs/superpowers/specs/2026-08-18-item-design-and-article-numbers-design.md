# Item Design and Multiple Article Numbers

**Date:** 2026-08-18  
**Status:** Approved for implementation planning  
**Scope:** Catalog item model, item entry/editing, article-number search, and pre-production data migration

## 1. Goal

Change the catalog so an Item is the parent entity identified internally by a
system-generated UUID, while one Item can have multiple article numbers.
Article numbers identify the same underlying item and therefore share the
item's commercial data: supplier, supplier cost, cost currency, minimum selling
price, low-stock settings, colors, and sizes.

The current `items.article_number` one-to-one model is replaced with a child
collection. The current `category` field is renamed to `design`; its values are
preserved as design values during migration.

Example:

```text
Item
├── name: T-shirt
├── design: Round neck
├── supplier / cost / minimum selling price
├── colors and sizes
└── article numbers: TS-001, TS-002, TS-003
```

## 2. Decisions

| Decision | Choice |
| --- | --- |
| Item identity | Existing system-generated UUID remains the canonical identity. |
| Item name | Required text field; the form provides an example hint such as `T-shirt`. |
| Design | Required text field replacing `category`; the form provides an example hint such as `Round neck`. |
| Article-number relationship | One-to-many: `items` → `item_article_numbers`. |
| Article-number uniqueness | Globally unique after trimming and case-normalizing. Uniqueness includes archived items because archived records remain in the system. |
| Article-number storage | Store the canonical normalized value; do not preserve case-only duplicates. |
| Article-number lifecycle | Create one or more numbers with an item, add more later, and remove numbers later. An item must retain at least one number. |
| Pricing | All commercial and pricing fields remain on `items`; there is no per-article-number pricing. |
| Existing fields | Supplier, colors, sizes, description, cost, minimum selling price, and low-stock settings remain. Only category is replaced by design. |
| Existing data | Existing `items.article_number` values are migrated into the child table. Existing category values become design values. |
| Search | Searching any article number returns its parent Item, preserving the current user workflow. |

## 3. Data model

### 3.1 `items`

Replace `article_number` with `design` in the Drizzle schema. Remove the
item-category relation and any item-category lookup behavior. The table keeps
its UUID primary key and all item-level commercial, inventory, color, size,
image, archive, and audit relationships.

The resulting catalog identity is:

```text
items.id                 — internal identity and foreign-key target
items.name               — item name
items.design             — required free-text design
item_article_numbers.*  — external article-number identifiers
```

### 3.2 `item_article_numbers`

Add a table with:

```text
id                UUID primary key, generated by the database
item_id           UUID not null, references items(id) with cascade delete
article_number    TEXT not null, canonical normalized value
created_at        TIMESTAMP not null
updated_at        TIMESTAMP not null
```

Add a unique constraint/index on `article_number` and an index on `item_id`.
The server normalizes input before insert/update by trimming surrounding
whitespace and applying a consistent case normalization. The database
constraint remains the final protection against concurrent duplicate writes.

The Drizzle relations expose `items.articleNumbers` and
`itemArticleNumber.item`.

## 4. Migration

Add one forward migration for the pre-production database:

1. Create `item_article_numbers` and its foreign key/indexes.
2. Copy every existing non-null `items.article_number` into
   `item_article_numbers` using the canonical normalization rule.
3. Detect normalized collisions before dropping the old column. If collisions
   exist, abort with a clear migration error so the values can be reviewed
   rather than silently assigning a number to the wrong item.
4. Rename `items.category` to `items.design`, preserving all existing values.
5. Remove `items.category_id`, its foreign key, and item-category-only schema,
   query, and UI code. The separate accounting transaction-category model is
   unrelated and remains unchanged.
6. Drop `items.article_number` and its old index after the copy succeeds.
7. Leave historical snapshot fields such as
   `supply_route_lines.article_number_snapshot` unchanged; they are historical
   text, not current catalog foreign keys.

All current stock, sales, transfers, returns, supply lines, notifications, and
audit relationships continue to reference `items.id`. They must not be
duplicated per article number. Current labels and audit resolution should join
through the parent item and render its article-number collection where a
current catalog label is needed.

## 5. Server behavior

### 5.1 Item create/update

The item input schema changes from `articleNumber` and `category` to:

```text
design: string, required
articleNumbers: string[], required on create with at least one value
```

Create runs in a transaction: normalize and validate all submitted article
numbers, insert the item, then insert its article-number rows. Duplicate
numbers within the request and numbers already belonging to another item
produce field-level, user-readable validation errors.

Updating item-level data does not require resubmitting the full article-number
collection. Article-number management is exposed through focused server
operations for adding and removing numbers. Removing the final number is
rejected. Every mutation checks ownership of the number and revalidates the
database uniqueness constraint.

The existing create/update permissions remain unchanged: administrators and
supervisors can manage catalog items; sales users can search and view them.

### 5.2 Search and lookup

`getItemByArticle` changes from a direct equality check on `items.articleNumber`
to a join through `item_article_numbers`. `searchItems` searches:

- article-number values in `item_article_numbers`; and
- item names in `items.name`.

Search returns one parent item per match, including all its article numbers,
colors, sizes/variants, supplier, and item-level pricing. Empty search results
and archived-item behavior remain unchanged.

All callers that currently use an item's single `articleNumber` must be updated
to use either the full article-number collection or an explicit selected number.
Historical snapshot values remain unchanged.

## 6. User interface

### Item editor

Replace the current category combobox with a required Design text input. Use
help text/placeholder examples rather than category lookup options:

- Item name: `T-shirt`
- Design: `Round neck`

Replace the single Article number input with a repeatable article-number
control. Users can type a number, add it to a visible list, remove it, and
submit multiple numbers. Existing numbers are shown while editing, and users
can add more without replacing the existing collection.

The UI normalizes values before submission and displays duplicate/conflict
errors next to the article-number control. Price, supplier, color, size, image,
and low-stock sections remain item-level and are not repeated for each article
number.

### Item list and detail

Item rows show the item name/design and its article numbers in a compact form.
The detail route continues to accept an article-number URL parameter, resolves
it to the parent item, and displays the complete article-number list. Any
navigation after create/update should use the item UUID or a valid article
number from the returned collection rather than assuming a single
`articleNumber` field on the item.

Supply, store, shop, POS, receiving, transfer, return, notification, and audit
surfaces should display article numbers through a shared item-label helper so
the one-to-many model is represented consistently.

## 7. Error handling and edge cases

- Blank item name or design is rejected before submission.
- Blank article numbers are rejected.
- Duplicate article numbers in one request are rejected before writing.
- A number belonging to another item is rejected, including when that item is
  archived.
- Concurrent duplicate inserts are caught from the database unique constraint
  and converted to the same user-readable conflict error.
- An item cannot be left without an article number.
- Archived items retain their article numbers and continue to block reuse.
- Historical records keep their original article-number snapshots even if the
  current item later gains or loses article numbers.
- Item UUIDs remain stable through migration and are never regenerated.

## 8. Testing and verification

### Unit/server tests

Add coverage for:

- article-number normalization;
- duplicate numbers within one create/update request;
- global duplicate rejection across different items;
- duplicate rejection against archived items;
- create with multiple article numbers;
- add and remove article numbers;
- rejection when removing the last number;
- search by any article number returning the same parent item;
- item-level pricing remaining shared regardless of article number;
- design replacing category in create/update payloads;
- migration backfill preserving item UUIDs and existing values.

Update existing item, supply, stock, sales, transfer, return, notification,
audit, and component fixtures to use `design` and article-number collections.

### End-to-end coverage

Cover the primary flow:

1. Create an item named `T-shirt` with design `Round neck` and multiple article
   numbers.
2. Search using the second article number and open the same item.
3. Add a new article number from the item detail/editor flow.
4. Attempt to reuse an existing number and verify the inline validation error.
5. Confirm the same supplier cost and minimum selling price are shown for the
   item regardless of which article number was used to find it.

Run typecheck, formatting/lint checks, the focused item/server tests, and the
existing regression suite before implementation is considered complete.

## 9. Out of scope

- Per-article-number pricing or supplier overrides.
- Article-number-specific stock, colors, sizes, or images.
- Reusing article numbers after archival.
- A separate design lookup/management table.
- Changes to accounting transaction categories.
- Rewriting historical audit or supply-line snapshot text.
